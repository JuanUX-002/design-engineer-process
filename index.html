El proceso completo

Design Engineer Process

Así se conecta todo:
desde que entendemos el problema hasta que el código queda publicado. No hace falta saber programar para seguir este mapa — cada caja es una etapa, y las flechas muestran qué le pasa la información a quién.

Pasa el cursor (o toca) cada caja para ver el detalle de esa etapa.

MCP

Es el protocolo que le permite a Copilot "leer" directamente el archivo de Figma — como si pudiera abrirlo y entender su estructura, sin que nadie tenga que exportar nada a mano.

Sistema de Diseño (DS Global)

Son los colores, tipografías, espaciados y componentes ya aprobados. Tanto Figma como el código final deben usar solo eso — nunca valores inventados.

Pull Request + Sonar

Es la revisión antes de publicar: alguien (o una herramienta automática) confirma que el código cumple los estándares del equipo. Si algo falla, vuelve a Copilot para corregirse.

01 · Por cada Historia de Usuario / pantalla

Flujo de trabajo, paso a paso

Toca cada paso para ver el detalle y marca la casilla cuando lo hayas completado. 0/9 completados

01 Investigar y reunir contexto ▾

Antes de tocar Figma: tener claro qué problema resuelve esta pantalla, para quién y por qué. Sin este paso, el resto del proceso genera una pantalla bonita que no responde a lo que el usuario o el negocio necesitan.

02 Tomar el frame exacto ▾

Copiar el link del frame específico en Figma (clic derecho → Copy link to selection) desde la HU correspondiente en la herramienta de backlog del proyecto. Nunca el link del archivo completo.

03 Inspeccionar — Prompt A ▾

Pedir solo estructura y tokens, explícitamente sin código todavía (plantilla en la sección 02). Esto evita que Copilot genere de una vez el HTML crudo de Figma.

04 Mapear al Design System del proyecto — Prompt B ▾

Cada elemento del árbol se empareja con un componente existente del DS. Solo si no hay match se justifica un componente nuevo.

05 Checklist de reducción ▾

Antes de aceptar el código: sin position: absolute (elementos con posición fija en vez de adaptarse a la pantalla), sin colores/medidas fijas, sin envoltorios vacíos, sin espacios duplicados en el mismo elemento.

06 Generar componente + test — Prompt C ▾

Un solo prompt pide componente y su test juntos — evita una segunda iteración solo para tests.

07 Security scan (solo si tocó backend) ▾

@maz-security-scan-skill sobre los archivos de integración modificados. Corrige credenciales y logging antes de seguir.

08 Commit estandarizado ▾

@maz-git-commit-skill con el Work Item de Azure DevOps: [AB#ID] ADD/UPDATE/FIX …

09 Push + PR ▾

El código se sube al repositorio y se abre un Pull Request (la solicitud para revisar y aprobar el cambio antes de publicarlo). Un chequeo automático valida el estilo, las pruebas y, cuando aplica, la seguridad del código (Snyk).

02 · Copiar, pegar, adaptar al proyecto

Plantillas de prompt

Están escritas para que Copilot no "improvise": cada una fija el alcance (un frame, no el archivo completo) y el resultado esperado, para no desperdiciar tiempo ni créditos en iteraciones de más.

Prompt A — Inspección (sin código)

agent · figma mcp
Usa el MCP de Figma sobre este frame exacto (no todo el archivo):
<pega aquí el link del frame>

Quiero solo:
1. Árbol de componentes y su jerarquía
2. Variables/tokens de color, tipografía y espaciado que usa (nombres, no valores hardcodeados)
3. Componentes de Figma que probablemente correspondan a algo del Design System del proyecto

No generes JSX ni CSS todavía. Solo el resumen anterior.

Prompt B — Mapeo al Design System del proyecto

agent
Con el árbol de componentes que acabas de leer, mapea cada elemento a un
componente del Design System del proyecto (ej. Button, Input, Select, Checkbox).

Para cada elemento sin match, dime explícitamente:
- por qué ningún componente existente cubre el caso
- qué props le faltarían al Design System para cubrirlo

No propongas librerías externas (MUI, Bootstrap, Ant, etc.) bajo ninguna circunstancia.

Prompt C — Componente final + test

agent
Genera el componente <NombrePantalla>.tsx para este proyecto
a partir del mapeo anterior, cumpliendo:

- Import solo desde el paquete del Design System del proyecto y su archivo de
  tokens (ej. './tokens.css') — nada de estilos en línea
- Sin position:absolute salvo overlays reales
- Sin colores/tamaños en px fijos — todo por variable de tokens o clases del DS
- Sin wrappers <div> vacíos
- TypeScript estricto, props tipadas explícitas (nada de `any`)

Incluye también <NombrePantalla>.test.tsx cubriendo el render base
y un caso de interacción, con el framework de testing del proyecto.

Prompt D — Security scan (solo backend/integraciones)

agent
@maz-security-scan-skill revisa src/services/<archivo modificado>

Reporta y corrige en el mismo paso cualquier credencial quemada, log inseguro
o validación de entrada faltante, según el checklist del skill.

Prompt E — Commit

agent
@maz-git-commit-skill subir los cambios de <NombrePantalla>, work item AB#<ID>
03 · Ser preciso también ahorra tiempo

Uso eficiente de Copilot (créditos y tokens)

GitHub Copilot factura por consumo real de tokens (entrada, salida y caché) según el modelo usado, no por un número fijo de "requests". Si el plan del equipo se agota antes de tiempo, no siempre hay downgrade automático — conviene ser precisos desde el primer prompt en vez de iterar a ciegas.

Qué gasta más
  • Prioriza Sonnet — es el modelo que mejor nos ha funcionado, con el mejor balance entre calidad y consumo. Reserva modelos premium como Opus para casos puntuales: consumen varias veces más por el mismo prompt.
  • Iterar "a ver qué sale" en vez de seguir la plantilla — cada vuelta del agente es una llamada nueva.
  • Pedir el archivo de Figma completo en vez de un frame puntual — el MCP devuelve mucho más contexto del necesario.
Cómo cuidarlo
  • Modelo base por defecto; premium solo con justificación puntual (pantalla con lógica compleja, no una pantalla estándar).
  • Siempre el frame exacto, nunca el archivo — usar "Copy link to selection" en Figma.
  • Reutilizar la documentación de tokens del Design System si ya existe, en vez de volver a consultar el MCP para lo que ya está documentado.
  • Agrupar pantallas similares en el mismo hilo de conversación en vez de abrir uno nuevo por cada una.

05 · Quién sostiene esto

Gobernanza mínima

Cuatro responsabilidades fijas — cada una con un dueño único — más una regla de convivencia con Git.

Regla Branches desde VS Code

Todo proyecto nuevo se crea desde VS Code — no desde el portal del repositorio — para que la extensión de Copilot y el MCP de Figma queden listos desde el primer commit. Convención: tipo/AB#ID-descripción. Solo se integra a la rama principal por Pull Request, nunca con push directo.

Dueño Repositorio

El tech lead o líder técnico del proyecto aprueba los Pull Requests, mantiene al día los permisos del equipo y decide cuándo un repo nuevo se justifica frente a un módulo dentro de uno existente.

Dueño Design System del proyecto

Una persona fija aprueba cualquier componente nuevo que se agregue, para que no se dupliquen variantes entre las distintas apps de un mismo proyecto.

Dueño Uso de Copilot

Revisa el consumo del equipo periódicamente y decide si se justifica pedir más seats o cambiar de plan.

Migración futuraCuando un proyecto conecte su Design System oficial/definitivo, el flujo de prompts es el mismo — solo cambia el paquete de destino.

07 · Cuando el Design System no alcanza

Nomenclatura para componentes custom

Aplica solo a lo que queda fuera del Design System: un componente nuevo que se justificó en el Pull Request porque ningún componente existente cubría el caso (ver 02 · Prompt B). El prefijo X hace visible, en el código y en Storybook, qué es Design System puro y qué es una excepción — así se detecta fácil cuándo una excepción merece subir al DS central.

No confundir con el Checklist de PREsto es distinto al ítem "Generación automática de nomenclatura para el equipo de diseño" de la sección 04 — aquella es una regla obligatoria del PR; esta tabla es la convención de nombres para cuando un componente custom queda justificado como excepción.
